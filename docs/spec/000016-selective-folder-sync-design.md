# Selective folder sync

Status: approved, 2026-10-30. The user approved folder selection as the first slice, followed by exploration of a Wails desktop UI.

## Intent and alternatives

Let a person choose which folders under one existing Drive root are synchronized by a Grove profile. Folder selection applies to the shared engine used by both `grove` and `groved`.

1. **Editable folder selection with retained local data (recommended).** Choose folders by stable Drive identity, allow later changes, and preserve files and tracking information when a selection is removed. This supports a normal selective-sync workflow but requires explicit transition and recovery rules.
2. **Choose only at profile creation.** Persist a fixed selection and require a new profile to change it. This is smaller but makes routine changes awkward and does not address existing profiles.
3. **Path and filename exclusion rules.** This would support broader filtering but introduces separate pattern, rename and precedence semantics. Defer it from this folder-first slice.

## User-facing behavior

- A profile defaults to the entire bound Drive root when no selection is configured. Existing current profiles continue to mean the entire root. Persist an explicit mode: `all` is distinct from an empty inclusion set, which means sync nothing. Deselecting the last selected folder must never revert to `all`.
- A user can inspect available owned My Drive folders under the bound root, select one or more folders, inspect the saved selection, and change it later. Selection identifies folders by Drive ID; names and paths are display information, not the identity. A selected folder includes its descendants and necessary ancestor directories. Selecting the root means the entire tree.
- Nested selections are allowed but redundant descendants are normalized away when an ancestor is selected. A child cannot be excluded beneath a selected parent in this slice; choose the desired child folders explicitly instead. A selected folder's identity and its ancestry must be verified within the bound root; an arbitrary supplied ID is not sufficient.
- Read-only folder discovery works before a profile exists using an explicit Drive root and token, through the existing authenticated Drive boundary and token-session locking. Initial profile creation accepts a repeated folder-ID inclusion option or an explicit empty selection, so a partial first sync never requires a full-root sync first. The complete initial selection is validated and persisted before any sync mutation; interruption resumes with the same selection rather than silently reverting to `all`.
- Folder discovery and changes are explicit CLI operations. An edit of an existing profile acquires the daemon lifetime lease and then the profile lock, holding both throughout validation and the state transition. Both are nonblocking; a running daemon or competing writer reports busy, and a simultaneous daemon start cannot race the edit. Do not expose secrets in errors or logs.
- Deselecting a folder stops syncing its contents but keeps existing local files and retained baseline information. It never trashes Drive data or deletes local files. Re-selecting a folder resumes only after safe reconciliation; it is not permission to upload or delete changes made while the folder was excluded.
- Directory paths outside selected subtrees are structural only where needed to reach a selected descendant. Unselected siblings and their local contents are not uploaded, removed, or considered deletion intent. A local addition inside an active selected subtree follows the existing explicit two-way rules.
- Selection changes are refused while a profile has any unfinished operation, recovery journal or unresolved conflict. An error explains the existing recovery or conflict action needed; changing selection never discards those records. An incomplete initial population must be completed or recovered before selection changes.

## Safety and reconciliation contract

- Store the selected folder identities and a monotonic selection revision in profile state. Maintain durable tracking for previously synced but currently excluded entries, including the baseline needed to distinguish retained data from new local additions. The active selection and retained records must be persisted atomically with their transition; a crash leaves either the previous or new selection recoverable. Never allow two profile writers.
- Model each affected subtree as active, pending population/reconciliation, or dormant, with its selection revision. `PopulationComplete` for the whole profile alone cannot enable writes in a newly selected subtree. Pending population advances only through journaled, recovery-safe work; completion is recorded durably before that subtree becomes active for two-way mutations. Dormant records retain their former local paths and baselines.
- The current code accepts profile-state versions 1–3. Treat a missing selection in those existing states as `all`, without discarding or reinterpreting pending recovery. Validate any new representation and reject unknown or malformed state. Persist a migrated representation atomically only when existing recovery permits it; pre-release policy does not require compatibility with older releases, but currently running profile data must remain safe.
- The edit itself changes only selection state; it does not mutate local or remote content. Validate the desired selected IDs, their ancestry and complete relevant listings before committing; if validation fails, retain the previous working selection. An explicitly removed old ID need not still be accessible, but its retained local data and baseline remain protected. Reconciliation happens in a later sync under the saved revision and its per-subtree gate. An explicit empty selection is a valid completed empty scope, not evidence that any item was deleted.
- A selection change is not a sync deletion. Removing a selection must not enqueue `OpTrash`, remove tracked local data, or interpret an absent local path as deletion. While excluded, local and remote changes are not acted upon.
- On re-selection, use the retained baseline to compare the current local and remote states. A local path missing while excluded is not deletion intent: preserve the remote item and plan a safe restoration. Any retained local edit requires an explicit decision before upload or overwrite, even if the remote side is unchanged. If both sides changed or an occupied path cannot be safely reconciled, surface an explicit conflict and require a decision. Do not automatically apply keep-local or keep-cloud policy to resolve ambiguity created during exclusion.
- Each newly selected or re-selected subtree has its own population/reconciliation gate. A globally populated profile does not authorize uploads or deletions in that subtree until its baseline is verified and the transition completes. Existing local files at newly included paths are never overwritten or silently uploaded.
- Local additions discovered during an excluded interval are not silently uploaded on re-selection. Preserve them and require an explicit reconciliation choice, including when a new remote item occupies the same path. A moved selected folder must not overwrite retained data at either its former or new path.
- A selected folder renamed or moved within the bound root remains selected by ID. Resolve its current path from a complete verified listing and apply existing move/collision safety checks. If a selected identity is missing, inaccessible, moved outside the bound root, or its location cannot be verified, fail closed and preserve data. An incomplete listing is never evidence of deletion.
- Never move an entire local directory if doing so would carry retained excluded or untracked descendants. Block that move with an explicit conflict until it can be resolved safely; include selected and structural ancestor renames in this rule. For a previously active item absent from the selected scan, verify its identity and ancestry before classifying it as moved out of scope; an unverified or missing identity fails closed rather than becoming a deletion.
- A remote item moving into selected scope is treated as pending reconciliation: use its retained baseline if previously tracked, or the new-subtree population gate if it was never tracked. Never overwrite an occupied local path or automatically upload a retained excluded local addition.
- A complete scan establishes the contents and ancestry of each selected subtree. Unselected subtrees are outside sync and deletion authority. If an unselected name or identity can collide with a selected path or ancestor, fail closed rather than overwrite it. The implementation may use complete metadata discovery under the root to establish ancestry, but must not require unsupported file content outside the selected scope to be synced.
- Discovery must consume every page for each listing used to prove a selected folder's ancestry or selected subtree. It may avoid descending into unselected subtrees once selection and path collisions are established; unsupported content outside scope must not authorize changes inside scope or force a transfer.
- Local scanning must skip excluded siblings before opening, statting, hashing or validating their contents, and must not treat them as untracked additions. Structural ancestor components needed to reach selected folders must still be verified as safe directories; a symlink or ambiguous collision on that path fails closed.
- A partial selection cannot distinguish a local deletion from a move into an unscanned excluded subtree. Therefore, a missing tracked local item under a partial selection must never automatically trash its Drive item, even under an automatic conflict policy. Surface a deletion conflict requiring an explicit user decision, then apply the existing full remote-subtree and baseline checks before any approved trash. Full-root `all` selection retains the existing deletion behavior.
- Existing two-way deletion rules apply only to entries that were active in the same confirmed selection revision, after complete local and remote scans for that revision. Folder deletion must never cover an excluded subtree or an unverified descendant. Selection changes, nested selections, parent/child overlap and remote moves must not expand deletion authority. A verified remote move out of scope retains its local data and baseline as excluded; it is not a remote deletion.
- An explicitly selected folder is a protected selection root. If that folder itself is missing locally, do not create a normal deletion conflict that can trash it: report a selection-repair condition, block the subtree and let the user restore it or explicitly remove its selection. This condition alone must not prevent that selection removal. Descendant deletions follow the partial-selection confirmation rule once the subtree is fully populated and verified.
- Recovery of a previously journaled operation uses the selection revision under which it was planned. Block edits while any operation, probe, transaction, candidate capture or conflict remains pending; complete or explicitly resolve recovery first. Never reinterpret a journal using a newer selection. Initial population and added-subtree progress must survive interruption without enabling two-way mutations prematurely.

## Boundaries and non-goals

This slice covers owned My Drive folders under the existing profile root. It does not add filename patterns, local path exclusion rules, automatic profile discovery, a graphical picker, shared drives, Google-native document conversion, or deletion of local data on deselection. The existing unsupported-name, duplicate-name, ownership and conflict policies continue to apply within the selected scope. Whether to offer a separate explicit local cleanup operation is a future decision.

## Verification

- Deterministic planning tests cover initial partial selection, nested/overlapping selections, structural ancestors, ignored siblings, stable IDs across rename/move, and safe failure on missing identities or incomplete listing.
- Transition tests cover deselect/reselect with unchanged files, local edits, remote edits, simultaneous edits, locally missing files, remote removal, collisions, unfinished journals and interruption at every persistence boundary. Include ancestor renames containing retained excluded siblings and verify those siblings never move. Assert no selection-only operation trashes Drive data or deletes local files.
- Two-way tests prove excluded paths never become upload or trash candidates; local moves into excluded scope never cause automatic trash; verified remote moves out of scope retain data; and approved deletion still requires complete, same-revision coverage. Test unreadable and symlinked excluded siblings, all versus empty selection, existing state versions, and per-subtree population gates. Check daemon-lease/profile-lock ordering, startup races, and daemon/CLI use of the same saved selection.
- Fake-provider process tests exercise initial selection, changes after stopping the daemon, restart, and recovery. Any authenticated Drive test requires explicit enablement, the dedicated test profile, disposable local directories and fixture-owned remote data.
- Linux and macOS offline, race, lint and build checks remain required. User desktop acceptance remains separate.

## Interface detail

Folder discovery displays IDs and paths; selection commands accept IDs. Names alone are not stable or unique identifiers.
